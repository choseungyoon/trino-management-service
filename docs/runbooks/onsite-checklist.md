## 0. 이번에 올라가는 것 — 기능 네 덩어리

`009` 이후로 쌓인 것이 네 개다. **각각 독립이고, 넷을 다 켤 필요는 없다.**
마이그레이션 열의 ✅ 는 2026-08-25 사내 적용분이다.

| | 기능 | 마이그레이션 | 필요한 설정 | 지금 |
|---|---|---|---|---|
| A | **리소스 그룹 편집** (FR-WL-07~10) | ✅ `010` `011` | `resource_groups.*` + Trino schema 권한 | 스키마만 올라감 — 검증(§6) 남음 |
| B | **Fleet 작업 실행** (FR-FL-04/05) | ✅ `012` `013` | `fleet.jobs` (**SSH 영향 있음 — D-009**) | 스키마만 올라감 — **켜지 않음** |
| C | **작업 보드** (FR-BOARD) | ✅ `014` `015` | 없음 (항상 켜짐) | **동작 중** (V-7 통과) |
| D | **벤치마크** (FR-BM-01/03/04/06) | ✅ `016` `017` · ⬜ `018` `019` | `benchmark.enabled` + Gateway + `ExecuteQuery` | 다음 차례 |

원래 권장 순서는 **C → A → D → B** 였다. C 는 끝났고 Gateway 도 붙었으니 **다음은 D** 다 —

## 2. ⛔ 마이그레이션 `010` → `019`

**`010`~`017` 은 2026-08-25 에 적용했다.** 남은 것은 `018` `019` 다 — 이 둘은 그날 이후
FR-BM-06(D-014, 쿼리 세트를 화면에서 관리)과 함께 추가되었다. 아래 절차는 그대로 쓰되
목록만 두 개로 줄인다.

- [ ] `git pull` → `pip install -e .` (Artifactory 프록시 경유)
- [ ] **재설치 후 명령이 넷 다 있는지 확인한다** — 콘솔 스크립트는 설치 시점에 만들어진다.
      `git pull` 만 해서는 새로 생긴 명령이 생기지 않는다 (`-e` 여도 마찬가지다).

```bash
ls venv/bin/tms-*    # tms-api  tms-collector  tms-config-check  tms-work-export
```

> 넷 중 하나라도 없으면 `pip install` 을 다시 한다. `tms-work-export` 가 없으면
> §7 의 보드 내보내기가 통째로 안 된다.
>
> **의존성이 셋 줄었다 (2026-08-27)** — `Jinja2` · `MarkupSafe` · `python-multipart`.
> 서버 렌더 콘솔이 삭제되면서(D-016) 템플릿도 폼 파싱도 없어졌다. venv 에 남아
> 있어도 해롭지 않으니 지우지 않아도 된다.
>
> **대신 이번 배포는 화면이 통째로 바뀐다.** 콘솔은 `/` 의 React SPA 이고,
> 주소가 몇 개 옮겨졌다 — 아래 표를 보고 북마크를 바꾼다.
>
> | 전 | 후 |
> |---|---|
> | `/clusters/<c>/resource-groups` | `/resource-groups?cluster=<c>` |
> | `/clusters/<c>/fleet` | `/fleet?cluster=<c>` |
> | `/clusters/<c>/restart` | `/restart?cluster=<c>` |
> | `/benchmarks/sets` | `/benchmark/sets` |
> | `/benchmarks/<id>` | `/benchmark/runs/<id>` |
> | `/clusters/<c>/health` | `/cluster-health?cluster=<c>` — ⛔ `/health` 는 liveness 프로브다 |
>
> ⛔ **번들은 저장소에 커밋돼 있다.** 배포 호스트에 Node 는 없고 필요하지도 않다 —
> `git pull` + `pip install` 이면 화면이 따라온다. 화면이 옛날 그대로라면
> `pip install` 이 안 된 것이지 빌드가 필요한 것이 아니다.

- [ ] `018` `019` 를 **번호순으로** `tms_owner` 로 적용
      <br>*(`009` 기준 환경이라면 `010`부터 `019`까지 전부. 이미 올라간 번호는 다시 돌리지 않는다)*

> 명령: `upgrade-r2-r3.md` §3 의 루프를 그대로 쓴다.

### ⛔ 번호순이 아니면 조용히 되돌아간다

`010` · `012` · `016` · `018` 은 각각 감사 액션 제약을 **`DROP` 후 다시 만든다.** 테이블 생성은
`IF NOT EXISTS` 라 재실행이 안전하지만, **이 제약은 아니다.** 나중 번호를 적용한 뒤
앞 번호를 다시 돌리면, 그 파일이 알던 목록으로 되돌아가면서 뒤에 추가된 액션이 사라진다.

```
018 적용 후 → … RESOURCE_GROUP_REVERT, FLEET_JOB_RUN, BENCHMARK_RUN, BENCHMARK_QUERY_CHANGE
010 을 재실행 → … RESOURCE_GROUP_REVERT                       ← 뒤의 셋이 사라짐
```

*(2026-08-24 로컬에서 실측했다. 추정이 아니다.)*

그 결과는 화면 오류가 아니라 **기능이 조용히 멈추는 것**이다 — 절대규칙 3 에 따라
감사 기록을 남기지 못하는 쓰기는 거부되므로, Fleet 작업과 벤치마크가 "감사 불가" 로 거절된다.

**따라서**: 번호순으로 한 번씩만. 중간에 실패하면 **거기서부터** 다시 시작하고,
앞 번호로 되돌아가지 않는다.

- [ ] `tms-config-check` 실행

> **게이트**: config-check 가 스키마 항목에서 실패하면 멈춘다. 이 검사는 테이블뿐 아니라
> **감사 액션 타입까지 대조**하므로, 위의 역순 사고가 났다면 여기서 이름을 대며 잡힌다.
> 통과하면 `010`~`019` 누락도 순서 사고도 없다.

- [ ] 감사 액션 목록에 `BENCHMARK_QUERY_CHANGE` 가 늘어 있다 (`018` 이 넣는다)
      <br>*(`009` 기준이라면 `RESOURCE_GROUP_CHANGE`·`RESOURCE_GROUP_REVERT`·`FLEET_JOB_RUN`·
      `BENCHMARK_RUN` 까지 다섯 개)*

**⚠️ 아직 서비스를 재시작하지 않는다.**

### 4-A. 리소스 그룹 편집

- [ ] Trino 가 **이미 `db` 매니저를 쓰고 있는지 먼저 확인** (D-010, 2026-08-14 적용분)

- [ ] OPA 카탈로그 규칙에서 `tms-svc` 가 데이터 카탈로그에 매칭되지 **않는** 것 재확인 — D-012 의 전제다

### 8-2. 실행 조건이 제대로 기록되는지 확인한다

**게이트는 2026-08-26 (D-015) 에 라벨로 바뀌었다.** 운영 중인 클러스터에서도 실행된다 —
확인할 것은 "거부되는가" 가 아니라 **"조건이 숫자를 따라다니는가"** 다.

- [ ] `/benchmark` 에 클러스터가 전부 나오고, 운영 중인 것은 **`Serving traffic`** 으로
      표시되며 이유가 그 줄에 문장으로 붙는다. **체크박스는 잠기지 않는다**
- [ ] 운영 중인 클러스터에서 실행 → 실행 화면에 **노란 배너**로 "트래픽을 받고 있었다"
- [ ] 실행 목록의 `Cluster was` 열이 **`Serving traffic`**
- [ ] ⛔ 같은 클러스터에 하나 더 실행 시도 → **거부된다** (두 실행이 서로를 측정한다)

> ⚠️ **무거운 세트를 운영 클러스터에 돌리는 것은 그 자체로 부하다.** 처음에는
> 가벼운 쿼리 한두 개짜리 세트로, 반복 1회로 시작한다. 재려던 느려짐을 스스로
> 만들 수 있다 (D-015).

### 8-2-1. 쿼리 세트를 만든다 (FR-BM-06)

세트는 이제 화면에서 만든다. 설정 파일에 없다.

- [ ] `/benchmark` → **New query set** → Set ID · 첫 쿼리 이름 · SQL 을 한 폼에 채운다.
      **Set ID 는 못 바꾼다**
- [ ] 쿼리 2~3개 더 추가 — 이 클러스터에 **실제로 있는 카탈로그**를 가리켜야 한다
- [ ] ⛔ `DELETE FROM ...` 을 저장해 본다 → **거부된다**
- [ ] ⛔ `-- 무해함` 다음 줄에 `DELETE` 를 넣어 본다 → **거부된다** (주석으로 못 가린다)
- [ ] 사유를 비우고 저장 → **거부된다**
- [ ] 감사 로그에 `BENCHMARK_QUERY_CHANGE` 가 사유와 함께 남았다

### 8-3. 통과 경로

- [ ] 대상 클러스터를 **사람이** 라우팅에서 제외 (Gateway UI 또는 안전 시퀀스 1단계)
- [ ] 실행 중 쿼리가 0 이 될 때까지 대기 → 그 줄이 **`Quiet`** 으로 바뀐다
- [ ] 클러스터를 **두 개 골라** 한 번에 실행 → 실행이 두 건 생긴다
- [ ] ⛔ 한쪽은 `Quiet`, 한쪽은 `Serving traffic` 인 두 실행을 비교 →
      **조건이 다르다는 경고**가 뜬다. 이게 게이트를 대신하는 안전장치다
- [ ] 벤치마크 화면이 **초록**으로 바뀐다
- [ ] 사유를 적고 실행 → 실행 화면이 5초마다 갱신된다
- [ ] 완료 후 쿼리별 중앙값·최소·CPU 가 채워진다
- [ ] 감사 로그에 `BENCHMARK_RUN` 이 사유와 함께 남았다
- [ ] **중지** 버튼: 다시 실행해서 중지 → 도는 쿼리가 끝난 뒤 `ABORTED`

> **TMS 는 클러스터를 라우팅에서 빼 주지 않는다.** 확인하고 거부만 한다 — 빼 주는 버튼이 있으면
> 그게 곧 안전 시퀀스를 건너뛰는 경로다 (절대규칙 5). 상세: `benchmark.md` §0

### 8-4. 비교 (FR-BM-03)

- [ ] 같은 세트를 **다른 클러스터**에서 한 번 더 실행
- [ ] 실행 화면에서 비교 → 쿼리별 차이와 판정(느려짐/빨라짐/차이 없음)이 나온다
- [ ] 다른 세트의 실행은 **선택지에 안 나온다**

### 8-5. 세트를 고쳐도 과거가 안전한지 (FR-BM-06)

**이게 세트를 Git 밖으로 꺼낸 대가를 확인하는 단계다.**

- [ ] 쿼리 하나의 SQL 을 고친다 (사유 필수)
- [ ] 고치기 전 실행 화면을 다시 연다 → **그 실행이 쓴 SQL 은 그대로다**
- [ ] 다시 한 번 실행한 뒤 이전 실행과 비교 → 그 쿼리 행에 **변경됨** 표시와 경고
- [ ] `/benchmark/sets/<키>/queries/<이름>/history` → 실행 한 건마다 그때 SQL 이 지금과 같은지 표시
- [ ] 실행 중에 같은 세트를 고쳐 본다 → **거부된다**

**append-only 확인** (`tms_app`, 둘 다 실패해야 정상)

- [ ] `UPDATE benchmark_result SET elapsed_ms = 1;`
- [ ] `DELETE FROM benchmark_result;`

## 11. 롤백

네 기능 모두 **기존 화면과 독립**이다. 문제가 나면 기능만 끄는 것이 먼저다.

| 증상 | 조치 |
|---|---|
| 벤치마크만 문제 | `benchmark.enabled: false` → `tms-api` 재시작 |
| 리소스 그룹 편집만 문제 | `resource_groups.enabled: false` → 재시작. **Trino 의 db 매니저와는 무관하다** — 화면만 사라지고 쿼리 수용은 그대로 돈다 |
| Fleet 작업만 문제 | `fleet.jobs` 를 비운다 → 재시작 |
| 보드만 문제 | 보드는 항상 켜져 있다. DB 를 못 읽으면 화면이 "보드를 읽을 수 없다" 를 표시하고 **다른 화면은 영향받지 않는다** |
| 기존 화면 회귀 | 코드 롤백 (`upgrade-r2-r3.md` §11) |

**마이그레이션은 되돌리지 않는다.** `010`~`019` 는 새 테이블과 감사 액션 다섯 개를 더할 뿐,
기존 테이블의 컬럼을 바꾸지 않는다. 코드를 이전 커밋으로 되돌려도 그 테이블은 그냥 안 쓰일 뿐이다.

⛔ **되돌리겠다고 앞 번호 마이그레이션을 다시 돌리지 않는다.** §2 의 이유로,
그건 롤백이 아니라 감사 액션 목록을 깎는 것이다.
