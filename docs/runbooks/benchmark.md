# 벤치마크 하네스 — 켜기 전에 읽는다 (FR-BM-01/03/04)

> **무엇에 쓰는가**: "왜 클러스터 A 가 B 보다 느린가". 그 질문 하나가 `FR-BENCHMARK` 를 R3 에서 R2 로 당긴 이유다.
> 설정 변경 검증, 업그레이드 회귀, 증설 효과 측정에도 같은 하네스를 쓴다.
>
> **근거**: `REQUIREMENTS.md` FR-BENCHMARK · `TRINO_VERIFIED.md` T1-5-1 · D-012(`ExecuteQuery`)

---

## 0. ⛔ 먼저 알아야 할 한 가지

**TMS 는 클러스터를 라우팅에서 빼 주지 않는다.**

FR-BM-04 는 "프로덕션 트래픽을 받는 클러스터에서 벤치마크를 돌리면 그 자체가 장애" 라고 못 박았고, 그래서 TMS 는 **제외 여부를 확인하고 거부만 한다.** 대신 빼 주지 않는 이유는 편의 문제가 아니다 — 유입 차단은 안전 시퀀스의 1단계로만 도달할 수 있고(절대규칙 5), 벤치마크 버튼이 백엔드를 비활성화할 수 있으면 **그 버튼이 곧 시퀀스를 건너뛰는 경로**다.

순서는 이렇게 된다:

1. 사람이 Gateway 에서 대상 클러스터를 비활성화한다 (또는 안전 재시작 시퀀스 1단계를 밟는다)
2. 실행 중 쿼리가 다 빠지기를 기다린다
3. TMS 벤치마크 화면이 **초록**으로 바뀐다
4. 그때 실행한다

3번이 초록이 아니면 화면이 무엇이 빠졌는지 문장으로 말한다. 그걸 읽고 고치는 것이 절차다.

---

## 1. 선행 조건

| 조건 | 왜 |
|---|---|
| `gateway.enabled: true` | 이게 없으면 TMS 는 클러스터가 라우팅에 있는지 **알 수 없고**, 모르는 상태는 제외된 상태가 아니다 → 전부 거부 |
| `tms-svc` 에 `ExecuteQuery` | 쿼리를 제출해야 한다. D-012 · `runbooks/executequery-grant.md` |
| 마이그레이션 `016` · `017` | `benchmark_run` / `benchmark_result`. `tms-config-check` 가 대조한다 |
| 쿼리 세트 선언 | 아래 §2. **기본 제공 세트는 없다** |

---

## 2. 쿼리 세트를 쓴다

`config.yaml` 의 `benchmark.query_sets` 에 선언한다. **화면에는 SQL 입력창이 없다** — 요청은 세트의 키만 고른다. SQL 을 받는 입력창은 CLAUDE.md 가 비목표로 명시한 웹 SQL 에디터이고, 이름만 바꾼다고 달라지지 않는다.

```yaml
benchmark:
  enabled: true
  default_repetitions: 3
  query_sets:
    adhoc:
      title: "Ad-hoc profile"
      description: "Superset 대시보드가 실제로 던지는 모양"
      queries:
        - name: scan_narrow
          sql: "SELECT count(*) FROM hive.reporting.events WHERE dt = DATE '2026-08-01'"
        - name: join_three
          sql: "SELECT n.name, count(*) FROM ... JOIN ... JOIN ... GROUP BY n.name"
```

**규칙 (전부 기동 시점에 검사한다 — 실행 중에 발견되지 않는다)**

| 규칙 | 이유 |
|---|---|
| 읽기 전용만 (`SELECT` `WITH` `SHOW` `EXPLAIN` `DESCRIBE` `VALUES` `TABLE`) | 세트는 **N회 무인 실행**된다. 복붙으로 섞여 들어간 `DELETE` 는 아무도 안 보는 클러스터에서 N번 돈다 |
| 한 문장만 (`;` 로 이어붙일 수 없다) | Trino 클라이언트 프로토콜이 한 요청에 한 문장이다. 두 번째 문장은 실행되지 않고 **첫 문장을 파싱 오류로 만든다** |
| 주석으로 첫 키워드를 가릴 수 없다 | `-- 무해함\nDELETE ...` 을 거른다 |
| 세트 안에서 이름 중복 불가 | 결과가 이름으로 키잉된다. 중복은 두 쿼리를 비교표의 한 칸으로 조용히 합친다 |
| 세트당 50개, 문장당 20,000자 | |

**세트를 바꾸면 과거 실행과 비교가 성립하지 않는다.** 같은 키의 세트를 손보면 예전 실행의 같은 이름이 다른 쿼리를 가리키게 된다. 내용을 바꿀 거면 **새 키를 만든다.**

---

## 3. 반복 횟수

기본 3. **1은 권하지 않는다** — 첫 실행은 나머지와 같지 않고(캐시·JIT·스플릿 배치), 1회면 중앙값이 곧 콜드 스타트다. 비교는 중앙값으로 하고, 그 중앙값이 이상치 하나에 끌려가지 않게 하는 것이 이 값의 용도다.

---

## 4. 결과를 읽는다

| 열 | 무엇 |
|---|---|
| 중앙값 | 반복 실행의 중앙값. 판정은 전부 이 값 기준 |
| 최소 | 가장 빨랐던 실행. "잘 됐을 때" 값 |
| CPU 중앙값 | Trino 가 보고한 `cpuTimeMillis`. 벽시계가 같은데 CPU 가 다르면 병렬도가 다른 것 |
| 처리 행 | ⚠️ Trino 최상위 `processedRows` 는 **사소한 쿼리에서 0 으로 온다** (T1-5-1). 참고용 |

**실패도 결과다.** 실패한 쿼리는 경과 시간과 Trino 쿼리 ID 를 달고 기록되며, **실행은 거기서 멈추지 않는다.** 세 번째 쿼리가 실패해서 멈추면 4~10번은 아무것도 측정하지 못하고, 그건 결국 사람이 손으로 돌려야 한다는 뜻이다. 전부 실패한 실행만 `FAILED` 다.

**보호 열이 "미확인" 인 실행의 숫자는 비교에 쓰지 않는다.** 그건 프로덕션 트래픽을 같이 측정한 값이다. 지우지 않고 남기되(증거를 지우는 게 더 나쁘다), 비교 화면이 매번 경고를 띄운다.

---

## 5. 비교 (FR-BM-03)

실행 화면에서 **같은 쿼리 세트의 다른 실행**만 고를 수 있다. 다른 세트의 같은 이름은 같은 쿼리가 아니다.

- 판정은 **쿼리별** 중앙값 차이다. 합계가 아니다 — 합계는 가장 긴 쿼리 하나가 지배하고, 그 하나에 가려지는 아홉 개가 대개 진짜 발견이다.
- ±5% 미만은 "차이 없음". 그 아래는 소음을 발견으로 포장하는 것이다.
- 한쪽에만 있는 쿼리, 한쪽에서 전부 실패한 쿼리는 **평균에 섞지 않고 따로 표시한다.**

---

## 6. 중지

실행 중 화면의 **중지**는 *지금 도는 쿼리가 끝난 뒤* 멈춘다. TMS 는 자기 쿼리를 죽이지 않는다 — 취소하면 코디네이터에 결과를 아무도 기록하지 못한 쿼리가 남고, 벤치마크의 쿼리는 어차피 스스로 끝난다(클러스터가 비어 있고 라우팅 밖이므로).

중지에는 사유를 받지 않는다. 멈추는 것은 **클러스터에 뭔가를 더 하지 않는 쪽**이고, 안전한 선택을 비싸게 만들 이유가 없다. 시작한 사람과 사유는 실행 행에 이미 남아 있다.

---

## 7. tms-api 가 재시작되면

실행 중이던 행은 기동 시 `UNKNOWN` 으로 표시된다. `FAILED` 가 아닌 이유: **이미 기록된 측정값은 진짜다.** 모르는 것은 나머지 세트가 돌았는지 여부뿐이다. 그 실행은 비교에서 경고를 달고 나온다.
