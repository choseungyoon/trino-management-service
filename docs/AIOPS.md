# TMS AIOps — AI Agent 기반 운영 자동화

**목표**: 서비스 운영 / 이상 감지 / 조치를 AI Agent가 수행하고, 인간은 **물리적 자원이 필요한 결정**(신규 서버 발급, 자원 증설 승인)에만 개입한다.

**핵심 원칙**: **자율성은 기능이 아니라 신뢰의 결과다.** 처음부터 자율 조치를 켜지 않는다. 신뢰는 데이터로 증명한 뒤 단계적으로 부여한다.

---

## 0. 먼저, 냉정한 진단

이 목표는 타당하지만 **가장 흔한 실패 경로가 명확**하다.

| 흔한 실패 | 왜 발생하나 |
|---|---|
| 이상 탐지 baseline이 없어 오탐 폭주 | 데이터를 쌓기 전에 탐지를 켠다 |
| 에이전트가 장애를 **증폭** | 조치가 잘못됐는데 반복 실행된다 |
| 조치 이력이 없어 원인 추적 불가 | 감사 없이 자동화를 붙인다 |
| 사람이 결국 다시 다 본다 | 신뢰가 없어 모든 알림을 재확인하게 된다 |

**따라서 순서가 결정적이다.**
`데이터 축적 → 탐지 정확도 검증 → 조치 제안 → 승인 후 실행 → 제한적 자율 실행`
이 순서를 건너뛰면 자동화가 아니라 자동화된 장애가 된다.

> Datadog Watchdog도 **정상 동작 baseline을 선제적으로 계산한 뒤** 그것을 기준으로 이상을 탐지한다. baseline 없는 이상 탐지는 존재할 수 없다.

## 1. 자율성 단계 (Autonomy Ladder)

| L | 단계 | AI 역할 | 인간 역할 | 진입 조건 |
|---|---|---|---|---|
| **L0** | 관측 | 데이터 수집·정규화 | 전부 판단 | 즉시 |
| **L1** | 해석 | 상태 요약, 이상 후보 제시, **원인 가설** | 판단·조치 | L0 데이터 30일+ |
| **L2** | 제안 | 조치 **플레이북 제안** (실행 안 함) | 승인·실행 | L1 오탐률 < 20% |
| **L3** | 대화형 실행 | **채팅으로 명령받아 실행** | 명령·확인 | L2 제안 채택률 > 70% |
| **L4** | 승인형 자율 | 스스로 탐지→조치안 생성→**승인 요청**→실행 | 승인만 | L3 무사고 90일 |
| **L5** | 제한적 자율 | **되돌릴 수 있는 저위험 조치만** 자율 실행 | 사후 검토 | L4 무사고 90일 + 조치별 개별 승인 |

**L5는 전체 자율이 아니다.** 조치 클래스별로 개별 승격하며, 아래 §3의 A/B 클래스만 대상이다. C/D 클래스는 **영구히 인간 승인**을 요구한다.

> 요청하신 "채팅으로 명령 → 나중에 자율"은 **L3 → L4/L5 경로**로 정확히 대응된다. 좋은 직관이다. 다만 L3 이전에 L0~L2가 반드시 선행되어야 한다.

## 2. 에이전트 구성

### `observer-agent` (L0)
- **역할**: 메트릭·이벤트·로그·헬스 상태 수집 및 정규화, 시계열 baseline 축적
- **권한**: 읽기 전용
- **산출물**: 정규화된 운영 상태 스냅샷

### `detector-agent` (L1)
- **역할**: 이상 후보 탐지, **정상 대비 무엇이 다른지** 설명
- **권한**: 읽기 전용
- **필수**: 모든 탐지에 **신뢰도(confidence)** 부여. 낮은 신뢰도는 억제
- **금지**: 조치 실행, 알림 직접 발송(초기)

### `diagnostician-agent` (L1~L2)
- **역할**: 원인 가설 생성 및 근거 제시. 쿼리 히스토리·리소스 그룹 상태·config drift·OPA 상태를 교차 조회
- **권한**: 읽기 전용
- **필수**: **가설임을 명시.** 단정 금지. 반증 근거도 함께 제시
- **강점 영역**: "특정 사용자의 쿼리가 리소스 그룹을 점유해 다른 그룹이 굶고 있다" 같은 **다중 신호 상관 분석** — 인간이 놓치기 쉬운 영역

### `remediator-agent` (L2~L5)
- **역할**: 조치 플레이북 선택·생성·실행
- **권한**: **조치 클래스별로 차등 부여** (§3)
- **필수**: 실행 전 dry-run, 영향 범위 산정, 롤백 계획 제시
- **절대 금지**: §4 가드레일 위반

### `reporter-agent` (전 단계)
- **역할**: 운영 리포트, 사후 분석(postmortem) 초안, 인간 요청 사항 정리
- **권한**: 읽기 전용
- **핵심 산출물**: **인간에게 보내는 자원 요청서** — "왜 필요한지, 얼마나 필요한지, 언제까지 필요한지, 안 하면 무슨 일이 생기는지"

## 3. 조치 클래스 및 권한 등급

**모든 조치는 4개 클래스 중 하나로 분류된다. 미분류 조치는 실행 금지.**

### Class A — 되돌릴 수 있고 영향이 국소적
| 조치 | 자율 가능 |
|---|---|
| 특정 쿼리 kill (임계 초과 폭주 쿼리) | L5 |
| 로그 레벨 일시 상향 (자동 만료 포함) | L5 |
| 캐시 갱신 / 헬스체크 재실행 | L5 |
| 알림 억제(downtime) 설정 | L5 |

### Class B — 되돌릴 수 있으나 영향이 넓음
| 조치 | 자율 가능 |
|---|---|
| 클러스터를 routing group에서 **비활성화** | L5 (조건부) |
| 워커 graceful shutdown | L4 |
| 리소스 그룹 임계값 임시 조정 | L4 |
| 라우팅 규칙 임시 변경 | L4 |

### Class C — 되돌리기 어려움
| 조치 | 자율 가능 |
|---|---|
| 클러스터/컴포넌트 재시작 | **불가 — 인간 승인 영구 필수** |
| 설정 변경 영구 적용 | **불가** |
| 카탈로그 등록/제거 | **불가** |
| 버전 업그레이드 | **불가** |

### Class D — 조직·비용·보안 결정
| 조치 | 자율 가능 |
|---|---|
| **신규 서버 발급 / 물리 자원 증설** | **불가 — 인간 전용** |
| OPA 정책 변경 | **불가 — Git PR 프로세스 전용** |
| 사용자 권한 부여/회수 | **불가** |
| 예산 관련 결정 | **불가** |

> **Class D가 "인간에게 요청"의 대상이다.** 에이전트는 여기서 **실행자가 아니라 신청자**다. `reporter-agent`가 근거를 갖춘 요청서를 만들고, 인간이 승인·실행한다.
>
> **OPA 정책을 Class D에 둔 이유**: policy-as-code를 Git으로 관리하기로 결정했다. 에이전트가 정책을 직접 바꾸면 그 결정이 무너진다. 에이전트는 **PR 초안까지만** 만들 수 있다.

## 4. 가드레일 (위반 시 즉시 정지)

| ID | 가드레일 | 이유 |
|---|---|---|
| **G1 — Blast Radius** | 단일 조치가 영향 줄 수 있는 노드/클러스터 수 상한. 초과 시 인간 승인 | 전면 장애 방지 |
| **G2 — Rate Limit** | 시간당 자율 조치 횟수 상한. 초과 시 자동 중단 + 알림 | 조치 폭주(자동화된 장애) 방지 |
| **G3 — Kill Switch** | 인간이 언제든 전체 자율 실행을 즉시 정지. **단일 명령, 승인 불필요** | 최후 방어선 |
| **G4 — No Cascade** | 동일 대상에 연속 조치 금지. 1차 조치 후 관찰 기간 필수 | 잘못된 조치의 반복 증폭 방지 |
| **G5 — Dry-run First** | Class B 이상은 dry-run 결과를 기록한 뒤 실행 | 예상치 못한 영향 사전 발견 |
| **G6 — Full Audit** | 모든 조치는 탐지 근거·가설·선택 이유·결과를 기록 | 사후 추적, 신뢰 축적의 근거 |
| **G7 — Degraded Mode** | 관측 데이터가 불완전하면 자율 조치 **전면 중단** | 눈 감고 수술하지 않는다 |
| **G8 — No Self-Modification** | 에이전트가 자신의 권한·가드레일을 변경 금지 | 자명 |
| **G9 — Query Path Isolation** | AIOps는 쿼리 실행 경로에 개입 금지 | NFR-ISOLATION 계승 |

> **G7이 특히 중요하다.** EventListener 수집이 끊겼거나 Prometheus가 다운된 상태에서 에이전트가 "이상 없음"으로 판단하고 조치하면 최악이다. **데이터 부재는 정상이 아니라 unknown이다.**

## 5. 조치 플레이북 (초기 세트)

각 플레이북은 **탐지 조건 / 가설 / 조치 / 검증 / 롤백**을 갖춘다. 이 구조가 없으면 플레이북이 아니다.

| 플레이북 | 탐지 | 조치 | 클래스 |
|---|---|---|---|
| PB-01 폭주 쿼리 | 단일 쿼리가 메모리/CPU 임계 초과 + 다른 그룹 큐 적체 | 해당 쿼리 kill + 사용자 통지 | A |
| PB-02 클러스터 응답 불가 | 헬스체크 연속 실패 | routing group에서 비활성화 | B |
| PB-03 워커 반복 크래시 | N회/M분 재시작 | 해당 워커 격리 + 인간 알림 | B |
| PB-04 리소스 그룹 기아 | 특정 그룹 큐 대기시간 급증 | 임계값 임시 조정 **또는** 인간 승인 요청 | B |
| PB-05 이벤트 수집 중단 | N분간 이벤트 0건 | **자율 조치 전면 중단** + 인간 호출 | G7 발동 |
| PB-06 OPA 사이드카 이상 | OPA 응답 실패/지연 | **즉시 인간 호출** (fail-closed = 전면 차단 위험) | C |
| PB-07 Config drift | 노드 간 체크섬 불일치 | 리포트 생성 + 인간 승인 요청 | C |
| PB-08 용량 부족 | 지속적 큐 적체 + 자원 포화 | **자원 증설 요청서 생성** | **D** |

> **PB-06 특별 주의**: OPA는 fail-closed다. Trino가 PDP에 도달하지 못하거나 PDP가 에러를 내면 **쿼리를 거부한다.** 즉 OPA 이상은 곧 전면 장애다. 에이전트가 추측으로 손대지 말고 **즉시 인간을 호출**해야 한다.

## 6. 인간 요청 인터페이스 (Class D)

에이전트가 인간에게 보내는 요청은 **아래 항목을 모두 갖춘다.** 하나라도 없으면 요청 생성 실패로 처리한다.

1. **무엇이 필요한가** — 구체적 사양 (워커 N대, 메모리 N GB)
2. **왜 필요한가** — 관측 데이터 근거 (큐 대기시간 추이, 자원 포화율)
3. **언제까지** — 긴급도 및 SLA 영향 시점
4. **안 하면 무슨 일이 생기는가** — error budget 소진 예측
5. **대안** — 증설 외 선택지 (워크로드 재배치, 리소스 그룹 조정)
6. **비용 추정** — 가능한 범위에서

> 이 형식을 강제하는 이유: "서버 더 주세요"는 승인받지 못한다. **데이터로 논증된 요청만이 조직을 움직인다.** 에이전트의 진짜 가치는 이 논증을 자동 생성하는 데 있다.

## 7. 신뢰 측정 지표

자율성 승격 여부를 **감이 아니라 데이터로** 결정한다.

| 지표 | 의미 | 승격 기준 예 |
|---|---|---|
| 탐지 정밀도 (Precision) | 탐지 중 실제 이상 비율 | L2 진입 시 > 80% |
| 탐지 재현율 (Recall) | 실제 이상 중 탐지 비율 | 실장애 대조 |
| 제안 채택률 | 인간이 에이전트 제안을 수용한 비율 | L3 진입 시 > 70% |
| 조치 성공률 | 조치 후 문제 해소 비율 | L4 진입 시 > 90% |
| 무사고 기간 | 에이전트 기인 장애 없는 기간 | 단계별 90일 |
| 오조치 건수 | 롤백이 필요했던 조치 | 0에 수렴 |

**모든 승격은 인간이 명시적으로 결정한다.** 지표 충족은 필요조건이지 충분조건이 아니다.

## 8. 단계별 도입 계획

| 단계 | 기간(안) | 내용 | 산출물 |
|---|---|---|---|
| **A0** | R1과 병행 | 데이터 축적 (L0). 스키마를 학습 가능하게 설계 | 정규화된 운영 데이터 |
| **A1** | R2 이후 | 이상 탐지 (L1). **알림 발송 없이** 섀도 모드로 정확도 측정 | 탐지 정확도 리포트 |
| **A2** | A1 3개월 후 | 조치 제안 (L2). 인간이 채택률 평가 | 플레이북 세트 |
| **A3** | A2 검증 후 | **채팅 인터페이스 (L3)** — 인간 명령 기반 실행 | 대화형 운영 콘솔 |
| **A4** | A3 무사고 90일 | 승인형 자율 (L4) | 승인 워크플로 |
| **A5** | A4 무사고 90일 | Class A/B 한정 자율 (L5) | 조치별 개별 승격 |

> **A1의 "섀도 모드"가 핵심이다.** 탐지를 켜되 아무에게도 알리지 않고, 실제 장애와 대조해 정확도만 측정한다. 이 기간 없이 알림을 켜면 오탐으로 신뢰가 먼저 무너지고, 그 뒤엔 아무리 정확해져도 아무도 안 본다.

## 9. 리스크

| 리스크 | 영향 | 완화 |
|---|---|---|
| 에이전트 오판으로 정상 클러스터 격리 | 서비스 축소 | G1 blast radius, G5 dry-run, 즉시 롤백 |
| 조치 반복으로 장애 증폭 | **치명적** | G2 rate limit, G4 no cascade, G3 kill switch |
| 관측 사각지대에서 오판 | 높음 | G7 degraded mode |
| 인간이 에이전트를 과신 | 중장기 위험 | 정기 수동 훈련, 사후 검토 의무화 |
| 자율성 승격을 조급하게 진행 | 높음 | 지표 기반 승격, 인간 명시 결정 |
| OPA 관련 자동 조치 | **치명적** | Class D 고정, 영구 인간 전용 |

## 10. 최종 권고

이 목표는 **기술적으로 달성 가능하지만 순서를 지켜야만** 가능하다.

가장 큰 유혹은 **L0~L2를 건너뛰고 바로 채팅 기반 실행(L3)으로 가는 것**이다. 채팅으로 명령하는 건 지금도 만들 수 있으니까. 하지만 그렇게 하면 에이전트는 **상태를 모르는 채 명령만 실행하는 리모컨**이 된다. 그건 자동화가 아니라 위험한 원격 조작이다.

**에이전트가 가치를 갖는 지점은 실행이 아니라 판단이다.** 판단은 데이터에서 나온다. 그러니 R1에서 쌓는 쿼리 히스토리와 헬스 데이터가 곧 AIOps의 연료다. **AIOps를 위해 별도로 뭘 만들 필요가 없다 — R1~R3을 제대로 만들면 그것이 AIOps의 기반이다.**
