TMS — R1 UI Design Proposal

Six screens and three overlays for the Trino Management Service portal. Dark-first operator console in the modern-monitoring idiom — the bar is Datadog, Starburst Enterprise, and Snowflake, deliberately not Cloudera Manager. All data below is synthetic sample data rendered in the real wire formats the backend already produces.

Theme dark default · light toggle Language English UI Accent Trino magenta Mode Operate — dense, scannable, fast

Design direction

Three ideas carry every screen. They come straight from the backend's design decisions, so the UI is the architecture made visible, not decoration on top of it.

  • Trust is the material. Every reading shows its freshness (the pulse in the top bar, stale badges); missing data renders as UNKNOWN with a written fix — never as green, never as an empty shrug. This is NFR-DEGRADE and health test H-09 as visual language.
  • Every alarm ships its remedy. Advice is a first-class element on the health screen — a readable card with a deep link, not a tooltip. This is the product's differentiator vs. a chart wall.
  • Writes are ceremonies. Kill/override flows show the target, demand a reason, and state the consequence ("shown to the query's owner"). The audit trail is one click away.

Type & density

  • System sans for all UI (the accepted best practice for operator tools; production will self-host a workhorse face — recommendation: Geist + Geist Mono).
  • Monospace only where it earns it: query IDs, SQL, measurements, timestamps — with tabular-nums everywhere digits align.
  • 13px data base, 1.2 scale, 36px table rows — dense but scannable; status never encoded by color alone (icon + word accompany every state).

Layout system

216px sidebar (product nav + external tool links + user/role) · 46px top bar (screen title, cluster context switch, freshness pulse) · fluid content, hairline-bordered panels, 8px radius, shadows only on overlays. Motion: 150–250ms state transitions only, no page choreography.

Screen 3 · Live Queries

The incident screen — and it opens on All clusters, because during an incident you don't yet know which cluster the hog is on. Filter chips double as the summary — the counts are the KPIs, attached to the controls that act on them. Long-running rows get an amber wash; kill is one deliberate click away, never accidental.

  • All is the default tab. The Cluster column appears only in the All view — switching to prod-a/prod-b drops it and the table tightens. Query IDs already betray their coordinator (…_wzn2d vs …_kx8fq), and the column makes it legible.
  • Freshness in All view shows the oldest cluster snapshot ("oldest of 2 clusters") — the merged list is only as fresh as its worst source.
  • Per-cluster degradation degrades alone: if one cluster's snapshot goes stale or untrusted (H-09), an inline strip names that cluster and its remedy while the other cluster's rows keep rendering. All-view never turns one cluster's problem into a blank page.
  • Chips are both summary and filter — no separate KPI card row to scan past. The long-running chip glows amber when its count is non-zero. In All view the counts aggregate and match Overview's per-cluster numbers.
  • Long-running rows: amber wash + 2px inset edge + bold elapsed. Loud enough to find, quiet enough to coexist with 200 rows.
  • Kill is an icon that turns red only on hover, and it never fires directly — it opens the ceremony (O2), which always names the cluster.
  • SQL preview lives in the drawer, not the table — rows stay one line tall at any width.
  • Health keeps per-cluster tabs only — the all-clusters health view already exists: it's the Overview screen.

Screen 4 · Cluster Health

The differentiator screen. Nine tests, each a verdict + the observed value + — when it's not GOOD — a written remedy with a deep link. UNKNOWN is honest and names its own fix (H-09's permission self-check shown below). Admins toggle tests inline; every toggle demands a reason.

  • Advice cards are the point — tinted ground, icon, plain-language remedy, deep link. Every CONCERNING/BAD state has one by database constraint; the UI just refuses to hide it.

The states we refuse to hide

These four banners are part of the design system, not error styling bolted on later. Each corresponds to a backend behavior that already exists and has a test.

System statesshared vocabulary across all screens
Data is stale — last collected 47s ago. The collector may be down or unable to reach prod-a. Values below are shown as of that time, never as current.
Write actions are disabled. The audit store is unreachable, and TMS does not perform actions it cannot record. Reads continue. AUDIT_UNAVAILABLE
Query list can't be trusted. The list is empty while JMX reports 38 running queries — most likely filtered by access control. Check tms-svc's queries: view grant in rules.json.
No queries running
Cross-checked against JMX (RunningQueries = 0) — prod-a is genuinely idle, not permission-filtered.
  • Stale ≠ broken, unknown ≠ empty, empty ≠ hidden — four distinct visual treatments for four distinct truths.
  • Even the empty state cites its evidence ("cross-checked against JMX") — that's H-09 working in the happy path.

What happens after approval

  • Implementation: server-rendered pages under src/tms/web/ against the existing FastAPI API — this design system as one small CSS token file, no heavy framework.
  • All-clusters view: served by fanning out the existing per-cluster endpoint (GET /clusters/:c/queries × N) and merging — or a thin aggregate endpoint if the fan-out proves awkward. Small backend addition, tracked for the build.
  • Production font: self-hosted Geist/Geist Mono (or IBM Plex) replaces the system stack; everything else carries over unchanged.
  • English advice strings: backend health advice is currently Korean — English equivalents needed (tracked).
  • Changes welcome: accent hue, density, sidebar contents, and the light theme's ground are all one-token edits. Tell me what to push on.
