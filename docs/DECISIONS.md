> **소유자**: `orchestrator`

## D-013 — 작업 보드를 만든다. 보드는 **상태**만 갖고, **근거**는 문서가 갖는다

| 항목 | 내용 |
|---|---|
| **날짜** | 2026-08-21 |
| **결정자** | Platform Owner (인간, 요청: "jira처럼 status를 admin이 볼 수 있게") |
| **상태** | 확정 |

**배경**: 관리자가 기능을 요청할 곳이 없었다. 그리고 이미 한 번 값을 치렀다 — `BACKLOG.md` 의 릴리스 배정과 `REQUIREMENTS.md` 부록 B 가 4건 어긋난 채로 한동안 굴러갔고, 어느 쪽이 맞는지 사람이 물어야 알 수 있었다. **같은 정보를 두 곳에 적으면 반드시 갈라진다.**

**결정**: TMS 안에 작업 보드(`/work`, FR-BOARD)를 만든다. 단, 무엇의 주인인지를 먼저 못 박는다.

| | 주인 |
|---|---|
| **보드**(DB) | **상태**. 결정 대기·차단·진행 중·완료. 자주 바뀌고, PR 을 보내지 않는 사람이 바꾼다 |
| **문서**(Git) | **근거**. 왜 그렇게 정했나. 리뷰를 거쳐 바뀐다 |

**어긋나면 문서가 이긴다.** 화면과 내보낸 파일 양쪽에 이 문장을 적어 둔다 — 규칙을 코드가 강제할 수 없을 때는 최소한 읽는 사람 눈앞에 둔다.

**보드에서 새로 만들 수 있는 것은 `request` 뿐이다.** 관리자가 화면에서 `decision` 을 만들 수 있으면 그 순간 `DECISIONS.md` 밖에 결정 기록이 생긴다 — 이 결정이 막으려는 바로 그것이다. 문서에서 온 항목은 문서가 준 키(`D-012`, `FR-BM-01`)를 그대로 쓴다. 채팅에 붙여넣는 식별자가 그것이기 때문이다.

**⛔ `docs/WORK_BOARD.md` 는 장식이 아니다**

보드는 사내망 DB 에 산다. "착수 전에 보드를 봐라" 는 지시는 **사외에서 그 DB 에 닿을 수 없는 사람에게는 실행 불가능한 지시**다. `tms-work-export` 가 만드는 파일이 그 간극을 메운다. 이 파일이 없으면 지시는 답한 것처럼 보일 뿐 답하지 않은 것이다.

**절대규칙 3 을 여기에는 적용하지 않는다 — 의도된 해석이다**

규칙 3(`reason` + 감사 + 확인)의 대상은 **Trino 를 향한 액션**이다. 댓글은 아무것도 건드리지 않는다. 사유에 사유를 요구하면 기능이 못 쓰게 되고, **맞지 않는 곳에 적용된 규칙은 맞는 곳에서도 진지하게 받아들여지지 않게 만든다.** 다만 규칙 3 이 실제로 지키려는 두 가지는 그대로 둔다:

- 보드 쓰기는 **admin 한정** (대상은 유지)
- 모든 쓰기가 **누가·언제**를 남긴다 (책임 추적은 유지)
- `reason` 필드와 `audit_action` 행은 **없다** — 댓글이 곧 사유이고, 보드 기록으로 감사 테이블을 채우면 운영자가 그 테이블을 여는 이유가 묻힌다

이 해석이 틀렸다면 `work/service.py` 의 `_require_admin` 한 줄을 고치면 된다. 조용히 넘기지 않고 코드와 여기에 적어 둔다.

**뒤집는 조건**: (1) 보드에 근거가 쌓이기 시작하면 — 즉 문서를 보지 않고 보드만 읽어도 되는 항목이 생기면 — 이 결정은 실패한 것이고, 그때는 문서를 보드로 옮기든 보드를 없애든 **하나로 합쳐야 한다.** (2) 요청이 아닌 종류를 화면에서 만들 수 있게 하는 변경은 이 결정을 다시 여는 것이다.

**관련**: `docs/WORK_BOARD.md`, `migrations/014_work_board.sql`, `src/tms/work/`, `CLAUDE.md` §현재 상태

## D-012 — `tms-svc` 에 `ExecuteQuery` 를 부여한다. 대신 A1 의 강제를 코드로 옮긴다

| 항목 | 내용 |
|---|---|
| **날짜** | 2026-08-21 |
| **결정자** | Platform Owner (인간, 트레이드오프 제시 후 선택) |
| **상태** | 확정 |

**배경**: `ARCHITECTURE.md` 원칙 A1 은 *"TMS 는 Trino 에 SQL 을 제출하지 않는다"* 이고, D-005 는 `queries` 규칙에서 **`execute` 를 빼는 것을 그 강제 수단**으로 삼았다. 그 결과 `system.runtime.nodes` 가 막혀 FR-FL-02(어느 워커가 미조인인지)와 FR-BM-01(표준 쿼리 세트 실행)이 함께 막혀 있었다.

**A1 이 이 순간을 예상해 두었다.** 원문:

> `system.runtime.*` 이 꼭 필요해지는 시점은 **R3 FR-FLEET 이며, 그때 저빈도 조회로 다시 판단한다.**

**결정**: 부여한다.

**근거 — A1 이 든 비용은 전부 빈도의 함수였다**

| A1 의 우려 | 5초 폴링일 때 | 이 설계에서 |
|---|---|---|
| 코디네이터의 쿼리·리소스그룹 슬롯 소비 | 상시 | **개수 불일치 시에만.** 평상시 0 |
| 하루 약 17,000건이 히스토리를 오염 | 17,000 | **평상시 0** |
| OPA 인가 호출 증가 | 상시 | 위와 같음 |

FR-FL-02 는 폴링이 필요 없다. 코디네이터의 `ActiveNodeCount` 와 인벤토리 개수가 어긋났을 때만 한 번 묻는다. FR-BM-01 은 `FR-BM-04`(타협 불가)에 따라 **라우팅 그룹에서 뺀 클러스터**에서만 돈다.

**FR-FL-02 하나만이었다면 부여하지 않았다.** 워커를 이름으로 짚는 값은 Trino Web UI 나 Ansible 로도 얻을 수 있어, 권한을 넓힐 이유로는 약하다. 결정을 뒤집은 것은 **FR-BENCHMARK 가 같은 권한에 걸려 영구히 막혀 있었다**는 사실이다 — "왜 클러스터 A 가 B 보다 느린가" 에 답할 유일한 수단이고, 부록 B 가 벤치마크를 R2 로 당긴 이유가 그것이다.

**받아들인 위험**: TMS 가 침해되면 임의 SQL 실행이 가능해진다. 그 파급의 크기는 **OPA 의 카탈로그 규칙이 `tms-svc` 에 무엇을 허용하는가**로 정해진다. `tms-svc` 가 catalog/schema/table 규칙에 매칭되지 않으면 `system.*` 만 도달하고 파급은 사실상 늘지 않는다. **부여와 함께 이 점을 확인·유지하는 것이 전제다.**

**⛔ A1 의 강제 수단을 대체한다**

`execute` 부재가 하던 일을 코드가 대신한다. 원칙 자체는 사라지지 않고 좁아진다:

> **A1(개정)**: TMS 는 **폴링 경로에서** SQL 을 제출하지 않는다. 수집기는 REST 와 JMX 만 쓴다.

| 대체 수단 | 무엇 |
|---|---|
| `clients/sql.py` | **SQL 을 제출하는 유일한 지점.** 다른 어디에도 두지 않는다 |
| import 가드 테스트 | `tms.collector.*` 가 그 모듈에 닿으면 **CI 가 실패한다.** 실수로 폴링 경로가 생기는 것을 사람의 기억이 아니라 테스트가 막는다 |
| 감사 | SQL 을 쓰는 액션은 다른 쓰기와 동일하게 `reason` + 감사 + admin |

**뒤집는 조건**: (1) `tms-svc` 가 카탈로그 데이터에 접근 가능해지면 권한을 회수한다 — 그 순간 파급의 크기가 달라진다. (2) 폴링 경로에 SQL 이 들어가면 A1 개정의 전제가 무너지므로, 가드 테스트를 지우는 변경은 이 결정을 다시 여는 것이다.

**관련**: `ARCHITECTURE.md` §1-1, D-005, `TRINO_VERIFIED.md` §T1-2-1

## D-011 — UI 는 서버 렌더 HTML 로 만든다. SPA 프레임워크를 도입하지 않는다

| 항목 | 내용 |
|---|---|
| **날짜** | 2026-08-14 (구현은 R1 부터. 이제야 근거를 기록한다) |
| **결정자** | Platform Owner (인간, "왜 React 를 안 썼나" 질문에 대한 논의 후) |
| **상태** | 확정 |

**배경**: `PRODUCT.md` 에 *"server-rendered HTML + vanilla JS or a light framework … no separate Node deployment"* 라는 **한 줄 제약만** 있었고 근거가 어디에도 없었다. 질문이 나왔다는 것이 곧 기록이 부족했다는 증거다.

**결정**: 화면은 FastAPI + Jinja2 서버 렌더로 만든다. React·Next.js·Vue 등 **별도 빌드와 Node 런타임을 요구하는 프레임워크는 도입하지 않는다.** 단일 파일로 vendoring 되는 경량 라이브러리(htmx, Alpine 등)는 이 결정에 배치되지 않는다.

**근거** — 일반적인 웹 개발이라면 SPA 가 기본값이다. 이 환경에서 그 기본값을 뒤집는 것은 네 가지다.

| | 내용 |
|---|---|
| **사내 레지스트리 제약** | 외부 직접 접근이 막혀 Artifactory 프록시를 거친다. 현재 런타임 의존성은 **직접 7개**다. Next.js 앱 하나면 전이 의존까지 수백 개가 되고, 등록·감사·갱신이 전부 그만큼 늘어난다 |
| **배포 단위** | K8s 없이 VM + systemd 확정(D-없음, 환경 사실). Node 런타임·빌드 툴체인·산출물 배포가 새로 붙는다. 지금 배포는 `git pull` + `systemctl restart` 두 줄이다 |
| **클라이언트 상태가 없다** | 컬렉터가 PostgreSQL 에 스냅샷을 쓰고 API 가 읽는다. 모든 화면이 "이 스냅샷을 그려라"다. SPA 의 상태 관리는 여기 없는 문제를 푼다 |
| **장애 중에 보는 화면** | 서버 렌더 HTML 은 번들이 깨져도, 브라우저가 낡아도 뜬다. 코디네이터가 죽어서 보는 화면이 같이 죽으면 안 된다 |

**그리고 비목표 목록이 이 결정을 지탱한다.** SPA 를 요구했을 기능이 전부 위임되어 있다 — 웹 SQL 에디터는 Superset, 차트·대시보드는 Grafana, 로그 검색은 Loki/OpenSearch. 남는 것은 **표와 폼**이다.

**인정하는 비용**: `web/static/tms.js` 가 237줄이고, 하는 일이 드로어 fetch·폴링 일시정지·fragment 갱신·폼 제출이다. **htmx 를 손으로 다시 만들고 있다.** 화면이 대부분 읽기 전용인 동안은 감당됐지만, FR-WL-07(리소스 그룹 편집)은 처음으로 진짜 인터랙티브한 화면이다.

**뒤집는 조건** — 아래 중 하나가 성립하면 재검토한다.

1. 비목표가 무너진다 (차트·에디터를 TMS 안에서 직접 그리기로 한다)
2. 실시간 협업 편집이 요구된다
3. 프론트 전담 인원이 생기고 화면이 수십 개 규모가 된다
4. 사내 npm 프록시가 정비되어 ①의 비용이 사라진다

**1~3 은 현재 비목표·규모·팀 구성상 오지 않는다.** 그래서 이 결정은 당분간 안정적이다.

**관련**: `PRODUCT.md` Stack, `CLAUDE.md` 비목표 표

## D-010 — 리소스 그룹을 `file` 에서 `db` 매니저로 옮기고, TMS PostgreSQL 의 전용 schema 에 둔다

| 항목 | 내용 |
|---|---|
| **날짜** | 2026-08-13 |
| **결정자** | Platform Owner (인간, 트레이드오프 제시 후 선택) |
| **상태** | 확정. **단 착수 전 아래 "선행 확인" 통과 필수** |

**배경**: 현재 약 50명 규모이고 `WORKLOAD_PROFILE.md` 에 데이터가 없다. `hardConcurrencyLimit`·메모리 한도의 적정값을 아무도 모르며, 안정화까지 반복 조정이 불가피하다. **`file` 매니저는 값 하나를 바꿀 때마다 코디네이터 재시작을 요구한다** — 그 비용이 곧 "그냥 안 고치기"로 이어진다.

**제시한 트레이드오프**

| | `file` (현행) | `db` (선택) |
|---|---|---|
| 값 변경 | **코디네이터 재시작** | `UPDATE` 후 **1초 반영** |
| 외부 의존 | 없음 (코디네이터 로컬 파일) | **DB 장애가 `max-refresh-interval` 을 넘기면 클러스터가 쿼리 수용을 중단** |
| 클러스터 2개 | 코디네이터마다 파일 사본 | `environment` 컬럼으로 **DB 한 곳에서 분리 관리** |
| 이력·리뷰 | Git | 없음 (테이블에 이력 컬럼이 없다) |

**결정**: `db` 매니저로 전환하고, **D-004 의 TMS 전용 PostgreSQL 인스턴스**에 전용 schema (`trino_resource_groups`) 를 만들어 둔다.

**Gateway DB 를 먼저 검토했으나 물렀다.** 두 가지 이유다.

1. **이름 충돌 위험.** Gateway 19 는 리소스 그룹 기능을 제거하면서 *"Existing resource group database tables are preserved and not dropped on upgrade"* 라고 명시했다 (`TRINO_VERIFIED.md` §T2-3). Gateway 의 DB 에는 `resource_groups`·`selectors`·`resource_groups_global_properties` 가 **정확히 같은 이름으로 남아 있을 수 있다.** 겹치면 Trino 는 테이블을 새로 만들지 않고 Gateway 가 남긴 스키마와 낡은 행을 읽는다.
2. **FR-WL-07(편집 화면)의 원자성.** TMS 가 리소스 그룹을 바꾸면 절대규칙 3 에 따라 감사 기록이 함께 남아야 한다. 같은 DB 면 **변경과 감사가 한 트랜잭션**이라 둘 중 하나만 성공하는 창이 없다. DB 가 갈리면 2PC 를 쓰거나 그 창을 감수해야 한다.

**받아들인 위험 — D-004 의 미해결 항목이 더 무거워진다**

D-004 는 *"이 DB가 죽으면 TMS 쓰기 액션이 전면 503"* 이라고 적고 **"가용성 설계를 별도로 검토해야 한다"** 를 남겨 뒀다. D-010 은 그 함의를 한 단계 올린다:

> **TMS DB 가 `max-refresh-interval`(24h) 을 넘겨 죽어 있으면, Trino 가 쿼리 수용을 중단한다.**

**NFR-ISOLATION 과의 관계**: 절대규칙 2 는 *"TMS 가 완전히 다운되어도 쿼리는 정상 실행"* 이다. 이건 여전히 성립한다 — TMS **애플리케이션**(API·컬렉터)이 죽어도 Trino 는 DB 를 직접 읽으므로 영향이 없다. 새로 생긴 의존은 애플리케이션이 아니라 **저장소**다. 다만 그 저장소를 운영하는 주체가 TMS 팀이라는 점에서, D-004 가 세운 "TMS 를 쿼리 경로에서 떼어 놓는다"는 방향이 **부분적으로 뒤집힌다.** 기록해 둔다.

**그래서 붙는 조건 4가지**

| 조건 | 이유 |
|---|---|
| `resource-groups.max-refresh-interval=24h` | 기본 `1h` 는 짧다. 하루면 TMS DB 재기동·마이그레이션 창을 Trino 가 아예 인지하지 못한다 |
| **전용 schema** `trino_resource_groups` | TMS 마이그레이션이 쿼리 수용 테이블에 도달할 경로 자체를 없앤다. TMS 마이그레이션 계정에 이 schema 권한을 주지 않는다 |
| **전용 DB 계정**, 테이블 생성 후 SELECT 로 축소 | 코디네이터는 읽기만 한다. 쓰기는 나중에 TMS 계정에만 준다 — "누가 이 값을 바꿨는가"를 계정 수준에서 답할 수 있게 된다 |
| **catch-all 셀렉터 필수** (`priority` 최저, 조건 없음) | 477 문서는 어떤 셀렉터에도 매칭되지 않는 쿼리의 동작을 규정하지 않는다. 그 상태를 만들지 않는다 |

**선행 확인 결과 (로컬 Trino 477 실측, 2026-08-13) — `TRINO_VERIFIED.md` §T1-4-1**

| 확인할 것 | 결과 |
|---|---|
| `?currentSchema=` 로 지정한 schema 에 테이블을 자동 생성하는가 | ✅ **그렇다.** 4개 테이블 전부. `public` 오염 없음 → schema 격리 성립, 별도 database 불필요 |
| DB 가 죽어 있을 때 코디네이터가 cold start 되는가 | ⛔ **아니다. 프로세스가 종료된다** |
| **돌고 있는** 코디네이터는 DB 가 사라져도 버티는가 | ✅ **버틴다.** 기존 사용자·**신규 사용자** 모두 쿼리 성공, DB 복구 시 재시작 없이 자가 회복 |

세 번째가 위험의 크기를 확정한다. **문제는 "DB 장애"가 아니라 "DB 장애 중의 재시작" 하나로 좁혀진다.** 그래서 아래 완화 1번(재시작 직전 도달성 확인)이 필요충분에 가깝다.

**부수 설정**: `resource-groups.refresh-interval` 을 기본 `1s` → **`10s`** 로 늘린다. DB 장애 중 재시도가 초당 1회이고 매번 스택 트레이스가 찍혀, 기본값이면 하루 장애에 코디네이터당 ERROR 약 8.6만 건이 쌓인다. 리소스 그룹 값은 자주 바뀌지 않으므로 반영 지연 10초는 무의미한 대가다. (`TRINO_VERIFIED.md` §T1-4-1 ③)

**⛔ 그래서 생긴 운영 제약 — `max-refresh-interval` 로 막을 수 없다**

`FlywayMigration.migrate()` 가 `Server.doStart()` 안에서 **HTTP 바인딩 이전에 메인 스레드로 동기 실행**된다. DB 가 닿지 않으면 재시도 없이 죽는다. `max-refresh-interval` 은 *돌고 있는* 코디네이터의 유예일 뿐 기동 경로와 무관하다.

> **리소스 그룹 DB 가 정지 중이면 두 클러스터의 코디네이터를 모두 재시작할 수 없다.**

그리고 코디네이터를 재시작해야 하는 순간은 대개 장애 중이며, 그때 TMS 쓰기 액션도 함께 503 이다 (D-004). **안전 시퀀스가 유입을 차단해 놓고 되살리지 못하는 조합이 성립한다.** 이것이 이 결정의 가장 큰 대가다.

**필수 완화 3가지**

| # | 조치 | 성격 |
|---|---|---|
| 1 | 안전 시퀀스(FR-CO-02) **4단계 진입 전 리소스 그룹 DB 도달성 확인**. 실패 시 재시작 단계를 거부하고, 이미 비활성화한 백엔드의 복구를 제안한다 | **코드** |
| 2 | `runbooks/` 에 *"리소스 그룹 DB 정지 중에는 코디네이터를 재시작할 수 없다"* 명시 | 문서 |
| 3 | ~~D-004 의 가용성 설계 검토~~ → **2026-08-13 인간 결정으로 해소.** TMS PostgreSQL 은 Gateway/VM1 과 **다른 호스트**에 있으며, **DB 가용성을 확보하기로 했다.** VM1 장애가 Gateway 와 리소스 그룹을 동시에 끊는 조합은 성립하지 않는다 | 해소 |

1번이 핵심이다. HA 를 갖춰도 창이 0 이 되지는 않고, 게이트 자체는 비용이 거의 없다. **못 살릴 것을 알면서 죽이는 경로만 막으면**, 나머지는 "DB 복구가 먼저"라는 평범한 순서 문제로 내려간다.

**뒤집는 조건**: (1) 위 두 확인 중 첫째가 실패하면 같은 인스턴스의 **별도 database** 로 간다. (2) TMS DB 장애로 쿼리 수용이 실제로 중단되면 리소스 그룹만 별도 인스턴스로 분리한다 — 그 시점엔 FR-WL-07 의 원자성을 포기하고 감사 기록을 best-effort 로 낮춰야 한다.

**관련**: `docs/templates/resource-groups-db.sql`, `docs/templates/resource-group.json`, `TRINO_VERIFIED.md` §T1-4 · §T2-3

## D-009 — 재시작 실행 방식은 설정으로 고르고, 기본값은 `manual` 로 둔다

| 항목 | 내용 |
|---|---|
| **날짜** | 2026-08-09 |
| **결정자** | Platform Owner (인간, 2026-08-08 트레이드오프 제시 후 선택) |
| **상태** | 확정 |

**배경**: FR-CO-02 안전 시퀀스의 4단계(재시작)를 누가 수행하느냐는 문제. 운영팀은 이미 Ansible 로 config·catalog 배포와 코디네이터/워커 재시작을 하고 있고, 클러스터별 인벤토리 파일(`cluster1.ini`, `cluster2.ini`)을 보유하고 있다.

**제시한 트레이드오프**

| | TMS 호스트에서 `ansible-playbook` 직접 실행 | 잡 러너 API (AWX/AAP) 경유 |
|---|---|---|
| TMS 가 갖는 권한 | **모든 Trino 노드에 대한 SSH** | 특정 job template 에 한정된 토큰 |
| 향후 TMS 취약점의 파급 | 전 노드 임의 실행 | 해당 job 실행뿐 |
| 운영자 경험 | 동일 | 동일 |
| 신규 인프라 | 없음 | AWX/AAP 도입 필요 |

**결정**: 운영팀이 **직접 실행**을 선택했다. 신규 인프라 없이 즉시 쓸 수 있다는 점이 결정적이었다.

**그래서 코드가 지는 책임** (`src/tms/ops/ansible.py`)

이 선택은 TMS 호스트가 전 노드 SSH 를 쥔다는 뜻이므로, **그 권한이 오직 관리자가 설정한 하나의 플레이북에만 쓰이도록** 만드는 것이 모듈의 유일한 목적이다.

| 제약 | 구현 |
|---|---|
| 플레이북은 입력이 아니라 **설정** | `config.yaml` 의 절대경로. 기동 시 존재 확인. 사용자 입력이 선택·변경·추가할 수 없다 |
| **셸을 쓰지 않는다** | `subprocess` 인자 리스트. 클러스터 이름이 탈출할 문자열 자체가 없다 |
| 대상은 **TMS 가 아는 클러스터만** | 이름은 인벤토리 파일을 고르는 데만 쓰이고 **명령행에 도달하지 않는다**. 호스트명이 argv 에 없으므로 오타겟팅 부류가 통째로 사라진다 |
| 타임아웃 | 워치독이 읽기 루프를 중단시킨다. 멈춘 플레이북은 단계를 실패시킬 뿐, 비활성 클러스터를 방치하지 않는다 |
| **확인하지 않은 성공을 주장하지 않는다** | 플레이북 실행 중 TMS 가 재시작되면 상태는 `unknown`. 추측으로 트래픽을 복구하지 않는다 |
| 출력 스트리밍 | 라인 단위로 흘려보낸다. 몇 분짜리 작업이 끝날 때까지 빈 화면이면 "진행 중"과 "멈춤"을 구별할 수 없다 |
| 비밀 마스킹 | 라인 단위 정규식. `vault_password`, `ansible_ssh_pass`, `AWS_SECRET_ACCESS_KEY` 포함 (실측으로 초기 정규식이 이들을 **전부 놓치고 있었음**을 확인하고 수정) |

**기본값은 `manual` 이다.** `cluster_ops.restart_mode: ansible` 로 명시해야 자동 실행이 켜진다. Ansible 이 설치되어 있다는 이유로 켜지지 않는다. 상태 기계·감사 기록·화면은 두 모드에서 완전히 동일하며, **사고를 막는 것은 게이트(빈 클러스터 확인 + 헬스 확인)이지 버튼을 누르는 주체가 아니다.**

**뒤집는 조건**: AWX/AAP 가 도입되면 `build_executor()` 에 실행기를 하나 추가하는 것으로 전환된다. 시퀀스·감사·화면은 바뀌지 않는다 — 어느 것도 재시작이 *어떻게* 일어나는지 알지 않기 때문이다.

## D-008 — 클러스터 목록의 추가·수정·삭제는 Gateway가 담당한다. TMS에 CRUD를 만들지 않는다

| 항목 | 내용 |
|---|---|
| **날짜** | 2026-08-07 |
| **결정자** | Platform Owner (인간) |
| **상태** | 확정 |

**배경**: 클러스터가 늘어날 때마다 `config.yaml` 을 직접 고치는 것이 번거롭고 휴먼에러 위험이 있다는 문제 제기가 있었다. 실제로 R1 실환경 배포 중 `trino.user` 오타로 전 헬스 테스트가 401로 막히는 일이 있었다.

**결정**: 그럼에도 **TMS에 클러스터 등록/수정/삭제 UI나 API를 만들지 않는다.** 클러스터 목록의 주인은 Trino Gateway다.

**근거**

1. **Gateway가 이미 한다.** `POST /gateway/backend/modify/add · update · delete`, `GET /gateway/backend/all` 이 존재한다 (`TRINO_VERIFIED.md` §T2-3). CLAUDE.md 절대규칙 4번 — 이미 있는 것을 다시 만들지 않는다.
2. **`config.yaml` 의 클러스터 목록은 애초에 임시다.** 파일 주석이 그렇게 밝히고 있다 — *"Gateway is disabled for now (B6), so this list is the source of truth."* 지금 CRUD를 만들면 임시 상태를 영구 기능으로 굳힌다.
3. **source of truth가 둘이 되는 편이 더 위험하다.** 라우팅이 아는 클러스터와 모니터링이 아는 클러스터가 갈라지면, 그 불일치는 평소에 안 보이다가 장애 때 드러난다. 편집의 번거로움보다 비싸다.

**영향**

| 대상 | 영향 |
|---|---|
| R1 | 변경 없음. `config.yaml` 이 계속 source of truth |
| **B6** | 우선순위 상승. 해소되어야 이 결정이 실효를 갖는다 |
| FR-GW-01 | 백엔드 목록 조회가 곧 클러스터 목록 조회가 된다. R2에서 TMS는 Gateway에서 목록을 읽고 `config.yaml` 의 `clusters` 는 폴백으로 축소 |
| 휴먼에러 완화 | CRUD 대신 **설정 검증 명령**으로 대응한다. **구현 완료 (2026-08-07)** — `tms-config-check`. 재시작 전에 URL·계정·권한·접속을 확인한다 |

**뒤집는 조건**: Gateway를 도입하지 않기로 확정되면 `config.yaml` 이 영구 source of truth가 되므로 재검토한다. 또는 클러스터 증감이 월 단위로 잦아져 Gateway 조작만으로 감당이 안 되는 것이 확인되면 재검토한다.

### 부기 (2026-08-07) — "TMS가 Gateway API를 호출하는 CRUD"는 이 결정이 막는 대상이 아니다

운영팀 회신 과정에서 **"TMS에서 Gateway API를 통해 CRUD 하면 좋겠다"** 는 제안이 나왔다. **이것은 위에서 반려한 것과 다른 제안이며, D-008을 근거로 반려해서는 안 된다.**

| | 반려한 것 | 새 제안 |
|---|---|---|
| 목록의 주인 | **TMS**(자체 DB) | **Gateway** (변함없음) |
| TMS의 역할 | 소유자 | **클라이언트** |
| 근거 3(이중 source of truth) | 해당됨 | **해당 없음** |

새 제안은 Gateway를 여전히 유일한 source of truth로 두고 TMS는 그 API를 호출하는 **화면**만 제공한다. 근거 3이 성립하지 않으므로 D-008의 반려 논리는 적용되지 않는다.

**오히려 유리한 점이 두 가지 있다.**

1. **TMS는 이미 Gateway API 쓰기 권한이 필요하다.** FR-CO-02 안전 시퀀스의 1단계(routing group 비활성화)와 5단계(재활성화)가 `POST /gateway/backend/deactivate|activate/{name}` 로 구현된다(§T2-3). 즉 Gateway 자격증명 보유는 이미 확정된 전제이고, add/update/delete 추가는 처음 보이는 것보다 작은 확장이다.
2. **감사 기록이 남는다.** Gateway UI에서 한 변경은 TMS 감사 로그에 없다. TMS를 경유하면 `reason` 필수 + `audit_action` 기록이 붙는다(절대규칙 3). "누가 왜 이 클러스터를 뺐나"에 답할 수 있게 된다.

**단, 확인된 제약**: Gateway 역할 모델은 `ADMIN` / `USER` / `API` 셋뿐이고 **읽기 전용 역할이 없다**(§T2-3). 목록 조회만 하려 해도 `API` 역할이 필요하며 그 역할은 변경 권한을 포함한다. 따라서 TMS가 쥐는 Gateway 자격증명은 **어차피 라우팅을 바꿀 수 있는 권한**이다. 이는 CRUD 구현 여부와 무관하게 성립하는 사실이므로, "권한이 커지니 하지 말자"는 반대 논거가 되지 못한다.

**판정**: **R2 FR-GATEWAY에서 다룬다.** R1 범위에 넣지 않는다 — R1은 읽기 전용 콘솔이고, 클러스터 변경은 파괴적 액션이라 안전 시퀀스(절대규칙 5)와 함께 설계해야 한다. R2 착수 시 `[NEEDS-HUMAN-DECISION]` 없이 진행 가능하다.

**관련**: `TRINO_VERIFIED.md` §T2-3, `BACKLOG.md` B6, `REQUIREMENTS.md` FR-GW-01·FR-GW-03

## D-007 — R1 인증은 로컬 계정으로 시작하고 AD 연동을 뒤로 미룬다

| 항목 | 내용 |
|---|---|
| **날짜** | 2026-08-06 |
| **결정자** | Platform Owner (인간) |
| **상태** | ✅ 확정 (**임시 조치**) |

**결정**: FR-PT-01의 AD/LDAP 연동을 R1에서 구현하지 않는다. 대신 **로컬 계정 + 임시 비밀번호**로 접속한다.

**⚠️ 조정한 부분 (AI 판단, 인간 확인 필요)**: 요청은 "admin 계정 하나"였으나 **이름 있는 로컬 계정 N개**를 지원하도록 만들었다.

> **이유**: 공유 `admin` 계정 하나면 모든 감사 기록의 `actor` 가 `admin` 이 된다. **"누가 이 쿼리를 죽였나"에 답할 수 없게 되며, 이는 FR-AUDIT-ACTION이 존재하는 이유 그 자체다.** 임시 인증 수단이 릴리스의 핵심 기능을 조용히 무력화해서는 안 된다.
> 구현 비용은 동일하다(계정 테이블이 1행이냐 N행이냐의 차이). 지금 계정 하나만 등록해 써도 되고, 나중에 사람별로 늘려도 코드 변경이 없다.

**구현 방식**

| 항목 | 내용 |
|---|---|
| 비밀번호 저장 | **PBKDF2-HMAC-SHA256, 600,000 iterations, 16바이트 salt.** 표준 라이브러리만 사용 (Artifactory 제약) |
| 평문 비밀번호 | **설정에서 거부한다.** `password` 키가 있으면 기동 실패. `password_hash` 만 읽는다 |
| 해시 생성 | `scripts/hash_password.py` — 운영자 로컬에서 실행. 평문이 터미널 밖으로 나가지 않는다 |
| 계정 위치 | `config.secret.yaml`(gitignore) 또는 환경변수. **`config.yaml` 금지 — 저장소가 PUBLIC(D-002)** |
| 세션 | 서명된 stateless 토큰. idle(기본 30분) + absolute(기본 12시간) 이중 만료 (FR-PT-03) |
| 세션 비밀키 | `TMS_SESSION_SECRET` 또는 `portal.session_secret`. **없으면 기동 실패** |
| 임시 비밀번호 | `must_change_password: true` → **변경 전까지 다른 API 전부 403** |
| 로그인 실패 | 5회/5분 잠금. 미존재 사용자와 오답을 메시지·시간 모두 구별 불가하게 처리 |

**알려진 한계 (수용)**

1. **로그아웃이 토큰을 서버측에서 무효화하지 못한다.** stateless 설계의 대가이며, idle 타임아웃이 유일한 상한이다.
2. **비밀번호 변경이 프로세스 재시작 후 사라진다.** 프로세스가 gitignore된 설정 파일을 소유하지 않기 때문이다. API가 새 해시를 응답으로 돌려주고, 운영자가 파일에 반영한다. 응답에 이 사실을 명시한다.
3. 세션 비밀키를 바꾸면 전 사용자가 로그아웃된다.

> **이 세 가지는 AD 연동으로 해소된다. 임시 모드임을 코드가 기동 시 WARN 로그로 알린다.**

**뒤집는 조건**: AD 연동(V9 재개) 시 `local_users` 를 비우면 로컬 인증이 자동 비활성화된다. 코드 제거 없이 전환 가능하다.

**관련**: `REQUIREMENTS.md` FR-PT-01, `docs/runbooks/local-account-setup.md`

## D-004 — TMS 자체 저장소는 신규 PostgreSQL 인스턴스

| 항목 | 내용 |
|---|---|
| **날짜** | 2026-08-06 |
| **결정자** | Platform Owner (인간) |
| **상태** | ✅ 확정 |

**결정**: 감사 로그(`audit_action`)와 헬스 이벤트(`health_event`)는 **TMS 전용 신규 PostgreSQL 인스턴스**에 저장한다.

**근거**

1. **규모가 작다** — 감사는 일 수백 건, 헬스 이벤트는 상태 전이 시에만. Elasticsearch를 검토할 이유가 없다.
2. **Gateway PostgreSQL과 분리한다** — Gateway DB는 쿼리 라우팅(queryId→backend 조회)에 관여하므로 **쿼리 경로의 일부**다. TMS가 부하를 얹으면 NFR-ISOLATION 취지에 어긋난다.
3. 감사 로그는 append-only + 정형 검색이다. 관계형이 맞다.

**함의**: 이 DB가 죽으면 **TMS 쓰기 액션이 전면 503이 된다** (AU1, 의도된 설계). 조회 기능도 스냅샷을 못 읽어 제한된다. → **가용성 설계를 별도로 검토해야 한다** (백업/복구 절차는 `sre-agent` 소관).

**B4와의 구분**: B4(대용량 쿼리 히스토리 저장소)는 **별개이며 여전히 미결**이다. D-001로 R1 범위 밖이 되어 통합 시점으로 이월됐다.

**관련**: `AUDIT_MODEL.md` §2, `ARCHITECTURE.md` §4

## D-005 — TMS는 전용 서비스 계정 `tms-svc` 를 쓴다 (`prometheus_scraper` 재사용 금지)

| 항목 | 내용 |
|---|---|
| **날짜** | 2026-08-06 |
| **결정자** | `trino-expert` 검증 → Platform Owner 승인 |
| **상태** | ✅ **확정 및 적용 완료 (2026-08-06)** — `rules.json` 규칙 추가, 계정 발급, `prometheus_scraper` 권한 축소 모두 완료 |

**결정**: TMS는 Trino 호출에 **전용 basic auth 계정 `tms-svc`** 를 사용한다. 기존 `prometheus_scraper` 계정을 재사용하지 않는다.

**근거**

1. **기능상 불가**: 현재 `rules.json` 의 `queries` 첫 규칙이 `prometheus_scraper` 에 `allow: []` 다. first-match-wins이므로 이 계정은 `view`·`kill` 이 전부 거부된다 → FR-QUERY-LIVE와 FR-QL-04가 동작하지 않는다.
2. **실패 방식이 위험**: `GET /v1/query` 는 403이 아니라 **빈 목록**을 반환한다(필터 기반 거부). "실행 중 쿼리 0건"으로 보여 한가한 정상 클러스터와 구별되지 않는다.
3. **감사 추적성**: 계정을 공유하면 Trino 측에서 "Prometheus 스크레이핑"과 "TMS 액션"을 구분할 수 없다.
4. **권한 분리**: `prometheus_scraper` 규칙을 TMS에 맞게 고치면, Prometheus 스크레이퍼에 쿼리 kill 권한을 주게 된다.

**필요 권한 (최소권한)**

| 섹션 | `tms-svc` | 비고 |
|---|---|---|
| `system_information` | `["read"]` | **`write` 없음.** R3 graceful shutdown 승인 시 추가 |
| `queries` | `["view", "kill"]` | **`execute` 없음** — 원칙 A1(TMS는 SQL을 제출하지 않는다)의 강제 수단 |

**부수 권고 (별건)**: `prometheus_scraper` 의 `system_information` 을 `["read","write"]` → `["read"]` 로 축소. 스크레이핑에는 `read` 만 필요하며, `write` 는 graceful shutdown 트리거 권한이다. **해당 계정은 아직 미사용이므로 지금 줄이면 비용이 0이다.**

**뒤집는 조건**: 계정 발급 자체가 불가능한 조직 제약이 있다면 `prometheus_scraper` 의 `queries` 규칙을 `["view","kill"]` 로 바꾸는 대안이 있으나, 위 3·4번 문제를 감수해야 한다.

**관련**: `ARCHITECTURE.md` §6-3-2, `TRINO_VERIFIED.md` §T3-6
