# TMS Agent Teams — Claude Code 운영 규칙

**프로젝트**: Trino Management Service (TMS)
**방법론**: AI-DLC (AWS AI-Driven Development Life Cycle)
**대상 도구**: Claude Code

---

## 0. AI-DLC 채택 배경

AI-DLC는 AWS가 2025년 7월 발표하고 그해 11월 워크플로 규칙을 오픈소스화(`awslabs/aidlc-workflows`)한 방법론이다. 핵심은 두 축이다.

- **AI 주도 실행 + 인간 감독**: AI가 상세 작업 계획을 체계적으로 만들고, 능동적으로 설명과 지침을 요청하며, **중대한 결정은 인간에게 미룬다.** 인간만이 비즈니스 요구사항에 대한 맥락적 이해를 갖기 때문이다.
- **동적 팀 협업**: AI가 정형 업무를 처리하는 동안 팀은 실시간 문제해결과 신속한 의사결정에 집중한다.

전통 SDLC는 인간 조정 비용이 크기 때문에 작업을 스프린트로 묶는다. AI-DLC는 **병목이 검증 속도로 옮겨갔다고 전제한다.** 그래서 스프린트는 **Bolt(수 시간~수일 단위 작업 주기)** 가 되고, 에픽은 **Unit of Work**가 되며, 단독 작성 + 비동기 리뷰는 **Mob 방식의 실시간 검증**이 된다.

3단계 구조: **Inception → Construction → Operations**
- Inception: Mob Elaboration으로 비즈니스 의도를 요구사항·스토리·작업 단위로 변환, 팀 전체가 AI의 질문과 제안을 검증
- Construction: Mob Construction으로 AI가 제안한 아키텍처·코드·테스트를 실시간 검증
- 두 의식(ritual)의 존재 이유는 **AI 산출물이 절대 맹목적으로 수용되지 않도록** 하는 것

> **중요한 한계 인식**: AI-DLC 공개 자료 어디에도 **누가 승인 권한을 갖는지, 에이전트가 작성한 코드의 평가 기준선이 무엇인지**는 정의되어 있지 않다.
> → **본 프로젝트는 이를 §4에서 명시적으로 정의한다.** 이것이 방법론을 그대로 베끼지 않고 우리 것으로 만드는 지점이다.

### 우리 프로젝트에 맞춘 조정

| AI-DLC 원형 | 우리 적용 | 조정 이유 |
|---|---|---|
| Mob Elaboration (팀 전체 동시 검증) | 1인 검증 + 체크리스트 | 현재 인력 구조상 mob 불가. 체크리스트로 대체 |
| Bolt = 수 시간~수일 | Bolt = 1~3일 | 프로덕션 데이터 플랫폼은 검증에 시간이 걸림 |
| 완전 자율 실행 | **읽기 작업만 자율, 쓰기 작업은 승인 게이트** | 프로덕션 Trino를 죽일 수 있음 |

## 1. 팀 구성 원칙

**원칙 1 — 에이전트는 역할이 아니라 "책임 경계"로 나눈다.**
"프론트엔드 개발자" 같은 직무명이 아니라, **어떤 코드/문서를 소유하고 무엇을 결정할 수 있는가**로 나눈다.

**원칙 2 — 모든 에이전트는 "검증 없이 단정하지 않는다"는 공통 규율을 갖는다.**
Trino 477 config property를 기억에 의존해 제안했다가 기동 실패를 유발한 이력이 있다. **모든 기술 가정은 공식 문서 확인 후 사용한다.**

**원칙 3 — 프로덕션에 쓰기를 하는 에이전트는 별도 승인 게이트를 통과한다.**

## 2. 에이전트 구성

### 2-1. `orchestrator` — 총괄 조정

**책임**
- Bolt 계획 수립, Unit of Work 분해, 에이전트 간 작업 배분
- 에이전트 산출물 통합 및 요구사항 추적성 관리
- **인간 결정이 필요한 지점을 식별해 에스컬레이션**

**소유 파일**: `docs/BOLTS.md`, `docs/DECISIONS.md`

**결정 권한**: 작업 순서/분해 (O) / 아키텍처 변경 (X — human) / 요구사항 변경 (X — human)

**필수 행동**
- 매 Bolt 시작 시 목표·완료 정의·리스크를 명시하고 **인간 승인을 받는다**
- `[NEEDS-HUMAN-DECISION]` 태그 발견 시 즉시 중단하고 질문
- 비목표(REQUIREMENTS.md §1-3) 침범 시도를 차단

---

### 2-2. `trino-expert` — Trino/Gateway/OPA 도메인 검증

**존재 이유**: 이 프로젝트의 최대 리스크는 "그럴듯하지만 틀린 Trino 지식"이다. 이 에이전트가 도메인 게이트키퍼다.

**책임**
- 모든 Trino/Gateway/OPA 관련 기술 가정을 **공식 문서로 검증**
- `[VERIFY]` 태그 항목 해소
- Trino API/SPI 연동 설계 리뷰

**소유 파일**: `docs/TRINO_VERIFIED.md` (검증 완료 사실만 기록)

**절대 규칙**
1. **Trino 477 공식 문서에서 확인하지 않은 config property, API 경로, SPI 시그니처를 제안하지 않는다.** 버전 간 삭제/변경이 잦다.
2. 검증 불가 시 "확인 불가"라고 명시한다. **추측으로 채우지 않는다.**
3. 검증 결과는 출처 URL과 함께 기록한다.

**우선 검증 대기열**
- [ ] EventListener SPI 시그니처 및 이벤트 필드
- [ ] graceful shutdown 엔드포인트 및 인증
- [ ] **런타임 로그 레벨 변경 API의 OSS 지원 여부** (미지원 시 FR-LOGLEVEL 폐기)
- [ ] 리소스 그룹 상태 조회 방법
- [ ] Gateway REST API 스펙
- [ ] OPA decision log 포맷

---

### 2-3. `backend-dev` — 백엔드 API 개발

**책임**: FastAPI 기반 TMS 백엔드, Trino/Gateway/OPA 연동 클라이언트, 인증·인가·감사 미들웨어

**소유 파일**: `src/tms/api/`, `src/tms/clients/`, `src/tms/core/`

**필수 준수**
- **NFR-ISOLATION**: 쿼리 실행 경로에 절대 개입 금지. 프록시 코드 작성 금지
- 모든 외부 호출은 타임아웃 + 서킷브레이커. 의존 컴포넌트 다운 시 해당 영역만 "unknown"
- 쓰기 API는 예외 없이 `reason` 파라미터 필수. 없으면 400
- 자격증명은 `config.secret.yaml`(gitignore) 분리
- 코드 주석은 **영어**
- Python 3.9+ 호환

---

### 2-4. `data-pipeline-dev` — 이벤트 수집 파이프라인

**존재 이유**: EventListener는 **코디네이터 프로세스 내부에서 동작한다.** 여기서 실수하면 프로덕션 Trino가 느려진다. 가장 위험한 컴포넌트라 별도 분리한다.

**책임**: EventListener 플러그인, 이벤트 저장 스키마, 보존/정리 정책

**소유 파일**: `src/event-listener/`, `src/tms/ingest/`, `docs/EVENT_SCHEMA.md`

**절대 규칙**
1. **이벤트 전송은 반드시 비동기 + 버퍼 + 백프레셔.** 저장소 다운 시 **이벤트를 버릴지언정 코디네이터를 블로킹하지 않는다.**
2. 코디네이터 부하 영향을 부하 테스트로 실측한다 (목표: CPU 1% 미만)
3. 스키마는 **향후 이상탐지 학습을 염두**에 두고 설계한다 (Datadog Watchdog 패턴은 P3이나 데이터는 지금부터 축적)

---

### 2-5. `frontend-dev` — TMS 웹 UI

**책임**: 포털/화면 구현, 역할 기반 화면 노출

**소유 파일**: `src/tms/web/`

**필수 준수**
- **자체 차트 구현 금지.** 메트릭 시각화는 Grafana 임베드/링크
- 파괴적 액션은 확인 다이얼로그 + 대상 명시 + reason 입력 필수
- 의존 컴포넌트 unknown 상태를 "정상"으로 표시하지 않는다

---

### 2-6. `sre-agent` — 관측성/알림/런북

**책임**: Prometheus 수집 설정, Alertmanager 룰, Grafana 대시보드, 런북, SLO 정의

**소유 파일**: `ops/prometheus/`, `ops/alertmanager/`, `ops/grafana/`, `docs/runbooks/`

**절대 규칙 (Datadog 알림 철학 차용)**
1. **모든 알림 룰은 `runbook_url` 라벨을 갖는다. 런북 없는 알림은 머지 금지.** 조치 없는 알림은 대응자의 시간을 낭비시킨다.
2. **증상에 알림을 걸고 원인에 걸지 않는다.** 사용자 영향(지연, 오류)에 호출하고, 모든 CPU 요동에 호출하지 않는다.
3. **No Data 처리를 명시한다.** 조용한 메트릭은 수집기 사망을 뜻할 수 있다.
4. 심각도 라우팅: P1=호출, P2=Slack
5. 계절성 메트릭에 고정 임계값 금지

---

### 2-7. `infra-agent` — 배포/증설 자동화

**책임**: systemd 유닛, Ansible playbook, 골든 이미지 정의, config drift 검사

**소유 파일**: `ops/ansible/`, `ops/systemd/`, `ops/packer/`

**필수 준수**
- systemd `User=`는 venv 소유자와 일치
- `Restart=on-failure` + `StartLimitBurst`로 반복 크래시 감지 (CM 패턴)
- 워커 축소는 **graceful shutdown 선행** 필수
- 사내 보안 제약: 외부 PyPI 직접 접근 불가, Artifactory 프록시 경유

---

### 2-8. `reviewer` — 품질 게이트

**존재 이유**: AI-DLC 자료가 정의하지 않은 "평가 기준선"을 이 에이전트가 담당한다.

**책임**: 코드 리뷰, 요구사항 추적성 검증, 아키텍처 원칙 위반 탐지

**소유 파일**: `docs/REVIEW_LOG.md`

**리뷰 체크리스트 (하나라도 실패 시 반려)**
- [ ] NFR-ISOLATION 위반 없음 (쿼리 경로 개입 없음)
- [ ] 쓰기 API에 reason 필수 + 감사 기록
- [ ] 비목표 기능이 추가되지 않음
- [ ] 검증되지 않은 Trino 가정 없음 (`trino-expert` 승인 확인)
- [ ] 자격증명 하드코딩 없음
- [ ] 코드 주석 영어
- [ ] 테스트 존재 및 통과
- [ ] 요구사항 ID 추적 가능

```
                    [ HUMAN — Platform Owner ]
                     승인 게이트 / 최종 결정권
                              ▲
                              │ 에스컬레이션
                        ┌─────┴──────┐
                        │orchestrator│
                        └─────┬──────┘
        ┌──────────────┬──────┼──────┬──────────────┐
        ▼              ▼      ▼      ▼              ▼
  trino-expert   backend-dev  │  frontend-dev   sre-agent
   (도메인 게이트)      │       │        │        infra-agent
        │              │  data-pipeline-dev       │
        └──────────────┴──────┼──────┴────────────┘
                              ▼
                         [ reviewer ]
                          품질 게이트
```

**규칙**
1. `trino-expert` 검증 없이 Trino 관련 코드 머지 금지
2. `reviewer` 통과 없이 머지 금지
3. `[NEEDS-HUMAN-DECISION]` 발견 시 전원 중단 → orchestrator가 에스컬레이션

## 4. 승인 게이트 — 인간 결정 사항

> **AI-DLC 원형이 정의하지 않은 부분을 여기서 명시한다.**

### 4-1. 인간 승인이 반드시 필요한 것

| 항목 | 이유 |
|---|---|
| Bolt 계획 착수 | 방향 오류 조기 차단 |
| 아키텍처 결정 (저장소 선택 등) | 되돌리기 비용이 큼 |
| 요구사항 추가/변경/삭제 | 범위 통제 |
| 프로덕션 대상 쓰기 기능 활성화 | 장애 리스크 |
| `[NEEDS-HUMAN-DECISION]` 전체 | 정의상 |
| 비목표 항목의 예외적 채택 | 범위 붕괴 방지 |

### 4-2. 에이전트 자율 범위

- 읽기 전용 조회 기능 구현 / 테스트 작성 / 문서 작성 / 리팩토링
- 공식 문서 검증 작업 / 로컬·개발 환경 실험

### 4-3. 평가 기준선 (Definition of Done)

| 항목 | 기준 |
|---|---|
| 테스트 커버리지 | 핵심 로직 80% 이상 |
| `reviewer` 체크리스트 | 전 항목 통과 |
| 요구사항 추적성 | 모든 코드가 FR-ID에 매핑 |
| 성능 | NFR-PERF 목표 실측 충족 |
| 문서 | 변경 사항이 문서에 반영 |

## 5. Bolt 운영

**Bolt 정의**: 1~3일 단위 작업 주기. AI가 제안한 계획을 팀이 검증하고, 에이전트가 실행하고, 결과를 리뷰한다.

**Bolt 진행 순서**
1. `orchestrator`가 Bolt 목표 + Unit of Work + 완료 정의 제시 → **인간 승인**
2. `trino-expert`가 관련 `[VERIFY]` 항목 선행 해소
3. 담당 에이전트 실행
4. `reviewer` 게이트
5. 인간 최종 확인 → 다음 Bolt

**Bolt 0 (필수 선행) — 검증 전용**
코드 작성 없이 `trino-expert`가 §2-2 검증 대기열을 전부 해소한다.
**FR-LOGLEVEL의 OSS 지원 여부 확인이 최우선.** 미지원이면 요구사항을 폐기하고 계획에서 제거한다.

> **Bolt 0을 건너뛰지 말 것.** 검증 없이 착수하면 존재하지 않는 API를 대상으로 코드를 짜게 된다. 과거에 정확히 이 실패가 있었다.

## 6. 공통 규율 (전 에이전트)

1. **모르면 모른다고 한다.** 그럴듯한 추측으로 채우지 않는다.
2. **공식 문서로 검증한다.** 특히 Trino 477 config property.
3. **비목표를 침범하지 않는다.**
4. **프로덕션 안전이 기능보다 우선한다.**
5. **코드 주석은 영어.**
6. **인간의 결정 영역을 침범하지 않는다.**
7. **AI 산출물은 맹목적으로 수용되지 않는다** — 이것이 AI-DLC Mob 의식의 존재 이유다.

## 7. 착수 방법

Claude Code에서 다음과 같이 시작한다.

```
Using AI-DLC, TMS 프로젝트를 시작한다.
docs/REQUIREMENTS.md, docs/MARKET_RESEARCH.md, docs/TEAMS.md를 읽고
Bolt 0(검증 전용) 계획을 제시하라.
코드 작성은 금지. 검증 대기열 해소만 수행한다.
```

> AI-DLC 오픈소스 규칙(`awslabs/aidlc-workflows`)을 함께 쓰려면 프로젝트 규칙 디렉토리에 배치하고 "Using AI-DLC, ..."로 시작하면 워크플로가 활성화된다. 다만 **AI가 생성하는 모든 계획을 신중히 검토하라**는 것이 해당 저장소의 명시적 경고다.
